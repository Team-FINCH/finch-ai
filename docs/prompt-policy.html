LLM에게 무엇을 주고, 무엇을 쓰게 하고, 무엇을 못 쓰게 할지 정의한다. 엔진이 계산한 값을 어떤 문장으로 바꿀 것인가에 대한 규칙 전부가 여기에 있다.

§1프롬프트 계층과 조립 순서

모든 기능이 하나의 조립 규칙을 공유한다. 계층을 나누는 이유는 두 가지다 — 고정 구간을 앞에 몰아 프롬프트 캐시를 태우기 위해서, 그리고 기능별 프롬프트를 고칠 때 공통 규칙이 흔들리지 않게 하기 위해서다.

┌─ L1 공통 시스템 고정 · 전 기능 동일 ─┐ │ │ ← 캐시 구간 └─ L2 기능별 시스템 고정 · 기능당 1개 ──┘ L3 사용자 Wiki 준고정 · 세션 내 불변 L4 엔진 출력 JSON 매 요청 변동 L5 RAG 문서 매 요청 변동 L6 대화 이력 chat 전용 L7 현재 요청 질문 · 기준시각
캐시를 조용히 깨뜨리는 것

현재 시각을 L1·L2에 넣으면 캐시가 매 요청 깨진다. 프롬프트 캐시는 접두 일치라서 앞쪽 1바이트만 바뀌어도 뒤가 전부 무효화된다. 기준 시각·요청 ID·사용자 이름은 반드시 L7에 넣는다. 같은 이유로 도구 목록의 순서도 고정해야 하고, JSON을 직렬화할 때 키 정렬을 켜야 한다.

§1.1공통 시스템 프롬프트

전 기능이 공유하는 L1이다. 이 안에 기능별 지시를 넣지 않는다.

L1 · Base System
당신은 국내 주식 투자자를 돕는 분석 도우미입니다. 사용자의 포트폴리오와 시장 데이터를 이해하고, 무슨 일이 있었는지 설명합니다. ■ 역할의 경계 - 당신은 계산하지 않습니다. 모든 수치는 제공된 엔진 출력에서만 가져옵니다. - 당신은 투자를 권유하지 않습니다. 매수·매도 의견, 목표주가, 가격 전망을 생성하지 않습니다. - 당신은 사실과 해석을 구분해 말합니다. 확인된 것과 추정한 것을 섞지 않습니다. ■ 수치 표기 - 비율·금액·수량·배수는 반드시 자리표시자로 씁니다: {{key}} - 사용 가능한 key는 요청마다 별도로 주어집니다. 목록에 없는 key를 만들지 않습니다. - 연도, 분기, 서수, 종목코드는 자리표시자 없이 그대로 씁니다. ■ 근거 - 외부 사실을 언급할 때는 근거 id를 붙입니다: [^cit_1] - 주어진 근거로 확인되지 않는 사실은 쓰지 않습니다. 추측으로 메우지 않습니다. - 데이터가 부족하면 부족하다고 씁니다. ■ 문체 - 존댓말을 씁니다. 이모지와 감탄사는 쓰지 않습니다. - 한 문장은 60자 이내를 지향합니다. - 전문 용어는 응답 내 첫 등장 시 한 번만 괄호로 풀어 씁니다.

"계산하지 않습니다"를 첫 번째 경계로 두는 이유는 이 서비스에서 가장 비싼 실패가 숫자 오류이기 때문이다. 모델은 지시가 없으면 주어진 값을 자연스럽게 반올림한다. 이 문장 하나로 전부 막히지는 않으므로 §5의 자동 검사와 함께 이중으로 방어한다.

§1.2토큰 예산과 캐싱

계층내용목표 토큰캐시
L1공통 시스템~1,200고정
L2기능별 시스템 + 예시~900고정
L3Wiki (profile + 해당 theses)~400세션 단위
L4엔진 출력 JSON~1,500변동
L5RAG 문서 (상위 6건)~4,000변동
L6대화 이력 (chat)~2,000변동
L7질문 · 기준시각~200변동

캐시 분기점은 L2 끝에 하나를 둔다. L1+L2가 약 2,100 토큰이라 최소 캐시 단위(약 1,024 토큰)를 넘는다. 분기점은 요청당 최대 4개까지 쓸 수 있지만, 나머지 계층은 매번 바뀌므로 추가해도 적중하지 않는다. 

system=[
  { "type": "text", "text": BASE_SYSTEM },
  { "type": "text", "text": FEATURE_SYSTEM,
    "cache_control": { "type": "ephemeral" } },   # ← 여기까지 캐시
]
적중 확인

배포 후 usage.cache_read_input_tokens를 반드시 확인한다. 반복 요청에서 이 값이 계속 0이면 어딘가에서 접두가 깨지고 있다는 뜻이다. 로그에 남기고 대시보드에 올려 둔다 — 조용히 실패하는 항목이라 지표 없이는 몇 주간 모른다.

§2답변 구조 표준

기획 단계의 Fact → Interpretation → Portfolio Impact → Risk → What to Watch 5단 구조를 모든 기능에 그대로 강제하지 않는다. 브리핑 한 항목을 5문장으로 쓰면 읽히지 않는다. 대신 기능별 축약형을 정의하고, Fact가 항상 첫 문장이라는 규칙만 공통으로 지킨다.

기능구조문장
Daily Briefing 항목Fact → Impact2
Stock Analyst 섹션Fact → Interpretation → Watch3–4
Thesis CheckFact → Interpretation → Watch4
Portfolio Doctor findingFact → Risk → Watch3
Why MovedFact → Impact3–4
Before You TradeFact → Impact2–3
Ask My Portfolio가변≤ 6

Fact를 앞에 두는 것은 문체 취향이 아니다. 해석이 먼저 오면 사용자가 근거를 검증할 기회를 잃는다. "집중도가 위험합니다. 반도체가 42.3%이기 때문입니다"와 "반도체 관련 자산이 42.3%입니다. 동일 업황에 함께 노출되어 분산 효과가 제한적입니다"는 같은 내용이지만 후자만 사용자가 전제를 확인하고 결론에 동의하거나 동의하지 않을 수 있다.

§3수치 표기 규약

모델은 자리표시자만 생성하고, 서버가 엔진 값으로 치환한다. 요청마다 사용 가능한 key 목록을 함께 넘긴다.

L4 · 엔진 출력 전달 형식
[사용 가능한 수치 자리표시자] {{semi_weight}} 반도체 업종 비중 {{semi_count}} 반도체 관련 보유 종목 수 {{n_eff}} 유효 종목 수 {{dr}} 분산 비율 목록에 없는 자리표시자를 쓰면 응답이 폐기됩니다. 수치를 직접 쓰지 마십시오. 반올림한 근사값도 허용되지 않습니다.

Structured Output으로 강제

자유 문장으로 받지 않고 스키마로 받는다. used_placeholders를 함께 받아 검증을 단순화한다.

output_config={
  "format": {
    "type": "json_schema",
    "schema": {
      "type": "object",
      "properties": {
        "narrative":          { "type": "string" },
        "used_placeholders":  { "type": "array", "items": { "type": "string" } },
        "used_citations":     { "type": "array", "items": { "type": "string" } }
      },
      "required": ["narrative", "used_placeholders", "used_citations"],
      "additionalProperties": False
    }
  }
}
프리필을 쓰지 않는다

JSON 출력을 강제하려고 assistant 턴에 {를 미리 넣는 방식은 현재 모델에서 400 오류로 거부된다. 반드시 위의 output_config.format을 쓴다.

주장 유형근거 필요예

마지막 줄이 위험 지점이다. "일반 상식"의 범위를 넓게 잡으면 근거 없는 서술이 그 이름으로 들어온다. 허용 범위를 교과서 수준의 메커니즘 설명으로 한정하고, 특정 종목·특정 시점에 대한 진술은 예외 없이 근거를 요구한다.

불확실성 표현을 세 가지로 고정하는 이유는 어조의 미세한 차이가 확신도로 읽히기 때문이다. "가능성이 높아 보입니다"와 "~로 보입니다"는 같은 근거에서 나왔더라도 사용자가 받는 신뢰도가 다르다. 표현이 늘어나면 근거 강도와 어조의 대응이 무너진다.

§4.2Wiki 인용 정책

Wiki 항목의 source에 따라 인용 어투가 달라진다. 이 구분을 어기면 "내가 언제 그랬어?" 문제가 발생한다.

source허용 어투단정
user_stated"말씀하신 대로", "~라고 하셨습니다"가능
derived_from_trades"거래 내역을 보면", "~에 매수하셨습니다"가능
ai_inferred"~하신 것으로 보이는데, 맞을까요?"질문형만
주문 점검에서의 제한

주문 전 점검의 wiki_conflicts는 user_stated 항목만 사용한다. AI가 추론한 성향으로 사용자의 주문에 이의를 제기하는 것은 근거 없는 참견이며, 개인화가 역효과를 내는 대표적인 경로다.

§5Guardrail — 입력단

질문을 네 갈래로 분류한다. 저지연이 필요하므로 별도의 경량 분류 호출로 처리한다.

분류예시 질문처리
normal"내 반도체 비중이 얼마야?"정상 처리
advice_seeking"뭐 사야 돼?", "지금 팔까?"재구성 후 대안 제시
prediction_seeking"이거 오를까?", "얼마까지 가?"재구성 후 대안 제시
out_of_scope투자와 무관한 질문범위 안내
거절이 아니라 재구성

못 한다고만 답하면 사용자는 기능을 다시 쓰지 않는다. 할 수 없는 것을 한 문장으로 말하고, 즉시 할 수 있는 것을 실제 데이터와 함께 제시한다. 이것이 이 서비스에서 규제 준수와 사용성이 만나는 지점이다.

사용자지금 삼성전자 더 사야 할까?
잘못된 응답죄송합니다. 투자 조언은 제공할 수 없습니다.
올바른 응답매수 여부는 말씀드릴 수 없습니다. 대신 판단에 필요한 것들을 정리해 드리겠습니다.

삼성전자는 현재 포트폴리오의 41.7%로, 이미 가장 큰 비중입니다. 추가 매수 시 비중이 어떻게 바뀌는지는 주문 화면에서 미리 확인하실 수 있습니다. 매수 시점에 남기신 논지는 "HBM 구조적 성장"이었고, 이후 확인된 변화는 종목 분석에 정리해 두었습니다.

재구성 응답도 §3의 자리표시자 규약을 그대로 따른다. 위 예시의 41.7% 역시 모델이 쓴 것이 아니라 치환된 값이다.

미래 단정의 대체가 핵심 패턴이다. 회사의 전망을 전달하는 것은 사실 보도이고, 같은 내용을 AI가 자기 목소리로 말하면 예측이 된다. 주어를 출처로 바꾸면 대부분의 미래 서술이 합법적인 사실 전달이 된다. 종목 분석의 "시장이 주목하는 요인"이라는 섹션명도 같은 원리로 정해졌다.

§5.2Guardrail — 출력단

생성 직후 순서대로 검사한다. 하나라도 걸리면 응답을 내보내지 않는다.

#검사실패 시
1스키마 준수 — 필수 필드 존재재생성
2미치환 자리표시자 — {{ }} 잔존재생성
3미허용 자리표시자 — 목록 밖 key 사용재생성
4원시 수치 — 비율·금액·수량·배수 직접 기입재생성
5엔진 값 대조 — 치환 결과가 엔진 출력과 일치차단
6근거 무결성 — 존재하지 않는 cit_id 참조재생성
7금지 표현 — §5.1 분류재생성
8Wiki 어투 — ai_inferred 단정 사용재생성
9길이 — 기능별 문장 수 상한재생성

5번만 재생성이 아니라 차단이다. 값이 어긋났다는 것은 파이프라인 어딘가가 고장났다는 뜻이므로, 다시 생성해서 우연히 맞기를 기대하면 안 된다. 즉시 GUARDRAIL_BLOCKED로 처리하고 알림을 띄운다.

7번은 정규식만으로 부족하다. "지금이 좋은 자리로 보입니다"는 금지어 목록에 걸리지 않지만 명백한 매수 권유다. 경량 분류 호출을 함께 태워 표현이 아니라 의미를 검사한다.

§7.1버전 관리

프롬프트는 코드가 아니라 데이터로 다룬다. 소스에 하드코딩하면 수정할 때마다 배포가 필요하고, 어떤 버전이 어떤 응답을 만들었는지 추적할 수 없다.

피드백과의 연결

API의 POST /feedback에서 수집하는 reasons가 이 문서의 우선순위를 결정한다. wrong_number가 많으면 §3과 출력단 검사를, too_generic이 많으면 §2의 구조와 Wiki 활용을 손본다. 프롬프트를 감으로 고치지 않기 위한 장치이므로 피드백 UI는 Phase 1부터 붙인다.

# 프롬프트와 응답 정책

LLM에게 무엇을 주고, 무엇을 쓰게 하고, 무엇을 못 쓰게 할지 정의한다. 엔진이 계산한 값을 어떤 문장으로 바꿀 것인가에 대한 규칙 전부가 여기에 있다.

**기본 모델** claude-opus-5 · **Thinking** adaptive · **출력** Structured Output · **언어** ko-KR

## §1 프롬프트 계층과 조립 순서

모든 기능이 하나의 조립 규칙을 공유한다. 계층을 나누는 이유는 두 가지다 — **고정 구간을 앞에 몰아 프롬프트 캐시를 태우기 위해서**, 그리고 기능별 프롬프트를 고칠 때 공통 규칙이 흔들리지 않게 하기 위해서다.

```
┌─ L1  공통 시스템        고정 · 전 기능 동일 ─┐
│                                             │  ← 캐시 구간
└─ L2  기능별 시스템      고정 · 기능당 1개 ──┘
   L3  사용자 Wiki        준고정 · 세션 내 불변
   L4  엔진 출력 JSON     매 요청 변동
   L5  RAG 문서           매 요청 변동
   L6  대화 이력          chat 전용
   L7  현재 요청          질문 · 기준시각
```

> **캐시를 조용히 깨뜨리는 것**
> **현재 시각을 L1·L2에 넣으면 캐시가 매 요청 깨진다.** 프롬프트 캐시는 접두 일치라서 앞쪽 1바이트만 바뀌어도 뒤가 전부 무효화된다. 기준 시각·요청 ID·사용자 이름은 반드시 L7에 넣는다. 같은 이유로 도구 목록의 순서도 고정해야 하고, JSON을 직렬화할 때 키 정렬을 켜야 한다.

## §1.1 공통 시스템 프롬프트

전 기능이 공유하는 L1이다. 이 안에 기능별 지시를 넣지 않는다.

**L1 · Base System**

```
당신은 국내 주식 투자자를 돕는 분석 도우미입니다.
사용자의 포트폴리오와 시장 데이터를 이해하고, 무슨 일이 있었는지 설명합니다.

■ 역할의 경계
- 당신은 계산하지 않습니다. 모든 수치는 제공된 엔진 출력에서만 가져옵니다.
- 당신은 투자를 권유하지 않습니다. 매수·매도 의견, 목표주가, 가격 전망을
  생성하지 않습니다.
- 당신은 사실과 해석을 구분해 말합니다. 확인된 것과 추정한 것을 섞지 않습니다.

■ 수치 표기
- 비율·금액·수량·배수는 반드시 자리표시자로 씁니다: {{key}}
- 사용 가능한 key는 요청마다 별도로 주어집니다. 목록에 없는 key를 만들지 않습니다.
- 연도, 분기, 서수, 종목코드는 자리표시자 없이 그대로 씁니다.

■ 근거
- 외부 사실을 언급할 때는 근거 id를 붙입니다: [^cit_1]
- 주어진 근거로 확인되지 않는 사실은 쓰지 않습니다. 추측으로 메우지 않습니다.
- 데이터가 부족하면 부족하다고 씁니다.

■ 문체
- 존댓말을 씁니다. 이모지와 감탄사는 쓰지 않습니다.
- 한 문장은 60자 이내를 지향합니다.
- 전문 용어는 응답 내 첫 등장 시 한 번만 괄호로 풀어 씁니다.
```

**"계산하지 않습니다"를 첫 번째 경계로 두는 이유**는 이 서비스에서 가장 비싼 실패가 숫자 오류이기 때문이다. 모델은 지시가 없으면 주어진 값을 자연스럽게 반올림한다. 이 문장 하나로 전부 막히지는 않으므로 [§5](#gate-out)의 자동 검사와 함께 이중으로 방어한다.

## §1.2 토큰 예산과 캐싱

| 계층 | 내용 | 목표 토큰 | 캐시 |
| --- | --- | --- | --- |
| L1 | 공통 시스템 | ~1,200 | 고정 |
| L2 | 기능별 시스템 + 예시 | ~900 | 고정 |
| L3 | Wiki (profile + 해당 theses) | ~400 | 세션 단위 |
| L4 | 엔진 출력 JSON | ~1,500 | 변동 |
| L5 | RAG 문서 (상위 6건) | ~4,000 | 변동 |
| L6 | 대화 이력 (chat) | ~2,000 | 변동 |
| L7 | 질문 · 기준시각 | ~200 | 변동 |

캐시 분기점은 **L2 끝에 하나**를 둔다. L1+L2가 약 2,100 토큰이라 최소 캐시 단위(약 1,024 토큰)를 넘는다. 분기점은 요청당 최대 4개까지 쓸 수 있지만, 나머지 계층은 매번 바뀌므로 추가해도 적중하지 않는다.

```
system=[
  { "type": "text", "text": BASE_SYSTEM },
  { "type": "text", "text": FEATURE_SYSTEM,
    "cache_control": { "type": "ephemeral" } },   # ← 여기까지 캐시
]
```

> **적중 확인**
> 배포 후 `usage.cache_read_input_tokens`를 반드시 확인한다. 반복 요청에서 이 값이 계속 0이면 어딘가에서 접두가 깨지고 있다는 뜻이다. 로그에 남기고 대시보드에 올려 둔다 — 조용히 실패하는 항목이라 지표 없이는 몇 주간 모른다.

## §2 답변 구조 표준

기획 단계의 `Fact → Interpretation → Portfolio Impact → Risk → What to Watch` 5단 구조를 **모든 기능에 그대로 강제하지 않는다.** 브리핑 한 항목을 5문장으로 쓰면 읽히지 않는다. 대신 기능별 축약형을 정의하고, **Fact가 항상 첫 문장**이라는 규칙만 공통으로 지킨다.

| 기능 | 구조 | 문장 |
| --- | --- | --- |
| Daily Briefing 항목 | Fact → Impact | 2 |
| Stock Analyst 섹션 | Fact → Interpretation → Watch | 3–4 |
| Thesis Check | Fact → Interpretation → Watch | 4 |
| Portfolio Doctor finding | Fact → Risk → Watch | 3 |
| Why Moved | Fact → Impact | 3–4 |
| Before You Trade | Fact → Impact | 2–3 |
| Ask My Portfolio | 가변 | ≤ 6 |

Fact를 앞에 두는 것은 문체 취향이 아니다. **해석이 먼저 오면 사용자가 근거를 검증할 기회를 잃는다.** "집중도가 위험합니다. 반도체가 42.3%이기 때문입니다"와 "반도체 관련 자산이 42.3%입니다. 동일 업황에 함께 노출되어 분산 효과가 제한적입니다"는 같은 내용이지만 후자만 사용자가 전제를 확인하고 결론에 동의하거나 동의하지 않을 수 있다.

## §3 수치 표기 규약

모델은 자리표시자만 생성하고, 서버가 엔진 값으로 치환한다. 요청마다 사용 가능한 key 목록을 함께 넘긴다.

**L4 · 엔진 출력 전달 형식**

```
[사용 가능한 수치 자리표시자]
{{semi_weight}}   반도체 업종 비중
{{semi_count}}    반도체 관련 보유 종목 수
{{n_eff}}         유효 종목 수
{{dr}}            분산 비율

목록에 없는 자리표시자를 쓰면 응답이 폐기됩니다.
수치를 직접 쓰지 마십시오. 반올림한 근사값도 허용되지 않습니다.
```

#### Structured Output으로 강제

자유 문장으로 받지 않고 스키마로 받는다. `used_placeholders`를 함께 받아 검증을 단순화한다.

```
output_config={
  "format": {
    "type": "json_schema",
    "schema": {
      "type": "object",
      "properties": {
        "narrative":          { "type": "string" },
        "used_placeholders":  { "type": "array", "items": { "type": "string" } },
        "used_citations":     { "type": "array", "items": { "type": "string" } }
      },
      "required": ["narrative", "used_placeholders", "used_citations"],
      "additionalProperties": False
    }
  }
}
```

> **프리필을 쓰지 않는다**
> JSON 출력을 강제하려고 assistant 턴에 `{`를 미리 넣는 방식은 현재 모델에서 400 오류로 거부된다. 반드시 위의 `output_config.format`을 쓴다.

## §4 근거 표기 규약

| 주장 유형 | 근거 필요 | 예 |
| --- | --- | --- |
| 엔진 계산 결과 | `type: engine` 자동 부착 | 비중, 변동성, 기여도 |
| 기업 사실 | 필수 | 실적, 공급계약, 지분 변동 |
| 시장 반응 서술 | 필수 | "시장이 주목하는 요인" |
| 일정 | 필수 | 실적 발표일, 배당 기준일 |
| 사용자 진술 인용 | `type: wiki` | 투자 논지 |
| 일반 상식 | 불필요 | "금리가 오르면 성장주가 영향받는 경향" |

마지막 줄이 위험 지점이다. **"일반 상식"의 범위를 넓게 잡으면 근거 없는 서술이 그 이름으로 들어온다.** 허용 범위를 교과서 수준의 메커니즘 설명으로 한정하고, **특정 종목·특정 시점에 대한 진술은 예외 없이 근거를 요구**한다.

## §4.1 톤과 문체

| 항목 | 규칙 |
| --- | --- |
| 어미 | `~습니다` / `~합니다`. 반말·개조식 금지 |
| 2인칭 | 대명사 대신 존대 어미로 처리 — "보유하신", "말씀하신". "당신"·"고객님" 미사용 |
| 이모지·감탄사 | 전면 금지 |
| 전문 용어 | 응답 내 첫 등장 시 괄호 설명 1회. 같은 응답에서 반복 설명 금지 |
| 문장 길이 | 60자 이내 지향. 한 문장에 두 가지 주장 금지 |
| 불확실성 | `~로 보입니다` / `~일 수 있습니다` / `확인되지 않았습니다` 세 가지만 사용 |
| 강조 | 굵게·느낌표 대신 문장 순서로 강조. 중요한 것을 먼저 쓴다 |

불확실성 표현을 세 가지로 고정하는 이유는 **어조의 미세한 차이가 확신도로 읽히기 때문**이다. "가능성이 높아 보입니다"와 "~로 보입니다"는 같은 근거에서 나왔더라도 사용자가 받는 신뢰도가 다르다. 표현이 늘어나면 근거 강도와 어조의 대응이 무너진다.

## §4.2 Wiki 인용 정책

Wiki 항목의 `source`에 따라 인용 어투가 달라진다. 이 구분을 어기면 "내가 언제 그랬어?" 문제가 발생한다.

| `source` | 허용 어투 | 단정 |
| --- | --- | --- |
| `user_stated` | "말씀하신 대로", "~라고 하셨습니다" | 가능 |
| `derived_from_trades` | "거래 내역을 보면", "~에 매수하셨습니다" | 가능 |
| `ai_inferred` | "~하신 것으로 보이는데, 맞을까요?" | 질문형만 |

> **주문 점검에서의 제한**
> 주문 전 점검의 `wiki_conflicts`는 **`user_stated` 항목만** 사용한다. AI가 추론한 성향으로 사용자의 주문에 이의를 제기하는 것은 근거 없는 참견이며, 개인화가 역효과를 내는 대표적인 경로다.

## §5 Guardrail — 입력단

질문을 네 갈래로 분류한다. 저지연이 필요하므로 별도의 경량 분류 호출로 처리한다.

| 분류 | 예시 질문 | 처리 |
| --- | --- | --- |
| `normal` | "내 반도체 비중이 얼마야?" | 정상 처리 |
| `advice_seeking` | "뭐 사야 돼?", "지금 팔까?" | 재구성 후 대안 제시 |
| `prediction_seeking` | "이거 오를까?", "얼마까지 가?" | 재구성 후 대안 제시 |
| `out_of_scope` | 투자와 무관한 질문 | 범위 안내 |

> **거절이 아니라 재구성**
> 못 한다고만 답하면 사용자는 기능을 다시 쓰지 않는다. **할 수 없는 것을 한 문장으로 말하고, 즉시 할 수 있는 것을 실제 데이터와 함께 제시**한다. 이것이 이 서비스에서 규제 준수와 사용성이 만나는 지점이다.

> **사용자**  
> 지금 삼성전자 더 사야 할까?

> **잘못된 응답**  
> 죄송합니다. 투자 조언은 제공할 수 없습니다.

> **올바른 응답**  
> 매수 여부는 말씀드릴 수 없습니다. 대신 판단에 필요한 것들을 정리해 드리겠습니다. 
 
삼성전자는 현재 포트폴리오의 41.7%로, 이미 가장 큰 비중입니다. 추가 매수 시 비중이 어떻게 바뀌는지는 주문 화면에서 미리 확인하실 수 있습니다. 매수 시점에 남기신 논지는 "HBM 구조적 성장"이었고, 이후 확인된 변화는 종목 분석에 정리해 두었습니다.

재구성 응답도 [§3](#numbers)의 자리표시자 규약을 그대로 따른다. 위 예시의 `41.7%` 역시 모델이 쓴 것이 아니라 치환된 값이다.

## §5.1 금지 표현과 대체

| 금지 | 예 | 대체 |
| --- | --- | --- |
| 매매 권유 | "지금이 매수 적기입니다" | 생성 금지 |
| 목표주가 | "10만 원까지 상승 여력" | 생성 금지 |
| 종목 간 우열 | "A보다 B가 낫습니다" | 생성 금지 |
| 손절·익절 조언 | "지금 정리하시는 편이" | 생성 금지 |
| 확률 단정 | "오를 가능성이 높습니다" | "다음 요인이 확인됩니다" |
| 인과 단정 
(conf < 0.6) | "실적 때문에 올랐습니다" | "같은 날 실적 발표가 있었습니다" |
| 미래 단정 | "실적이 개선될 것입니다" | "회사는 개선을 전망했습니다[^cit_1]" |
| 감정 유도 | "지금 놓치면 후회할" | 생성 금지 |
| 위험 축소 | "크게 걱정하지 않으셔도" | 생성 금지 |

**미래 단정의 대체가 핵심 패턴**이다. 회사의 전망을 전달하는 것은 사실 보도이고, 같은 내용을 AI가 자기 목소리로 말하면 예측이 된다. **주어를 출처로 바꾸면 대부분의 미래 서술이 합법적인 사실 전달이 된다.** 종목 분석의 "시장이 주목하는 요인"이라는 섹션명도 같은 원리로 정해졌다.

## §5.2 Guardrail — 출력단

생성 직후 순서대로 검사한다. 하나라도 걸리면 응답을 내보내지 않는다.

| # | 검사 | 실패 시 |
| --- | --- | --- |
| 1 | 스키마 준수 — 필수 필드 존재 | 재생성 |
| 2 | 미치환 자리표시자 — `{{ }}` 잔존 | 재생성 |
| 3 | 미허용 자리표시자 — 목록 밖 key 사용 | 재생성 |
| 4 | 원시 수치 — 비율·금액·수량·배수 직접 기입 | 재생성 |
| 5 | 엔진 값 대조 — 치환 결과가 엔진 출력과 일치 | 차단 |
| 6 | 근거 무결성 — 존재하지 않는 `cit_id` 참조 | 재생성 |
| 7 | 금지 표현 — [§5.1](#forbidden) 분류 | 재생성 |
| 8 | Wiki 어투 — `ai_inferred` 단정 사용 | 재생성 |
| 9 | 길이 — 기능별 문장 수 상한 | 재생성 |

**5번만 재생성이 아니라 차단이다.** 값이 어긋났다는 것은 파이프라인 어딘가가 고장났다는 뜻이므로, 다시 생성해서 우연히 맞기를 기대하면 안 된다. 즉시 `GUARDRAIL_BLOCKED`로 처리하고 알림을 띄운다.

7번은 정규식만으로 부족하다. "지금이 좋은 자리로 보입니다"는 금지어 목록에 걸리지 않지만 명백한 매수 권유다. **경량 분류 호출을 함께 태워** 표현이 아니라 의미를 검사한다.

## §6.1 호출 파라미터

| 파라미터 | 값 | 비고 |
| --- | --- | --- |
| `thinking` | `{"type": "adaptive"}` | 고정 예산 방식은 현재 모델에서 400 오류 |
| `output_config.effort` | 위 표 참조 | `output_config` 안에 넣는다. 최상위 아님 |
| `output_config.format` | 기능별 JSON Schema | 구버전 `output_format` 아님 |
| `max_tokens` | 비스트리밍 16,000 / 스트리밍 64,000 | 낮게 잡으면 문장 중간에 잘린다 |
| `temperature` | 사용 불가 | 현재 모델에서 제거됨. 400 오류 |
| assistant 프리필 | 사용 불가 | 400 오류. Structured Output으로 대체 |
| 스트리밍 | chat · analysis | 긴 출력에서 HTTP 타임아웃 방지 |

> **재현성에 대한 주의**
> `temperature`를 쓸 수 없으므로 **출력을 완전히 고정할 방법이 없다.** 평가 체계에서 "동일 조건 일관성"을 볼 때 이 점을 전제해야 하며, 문자열 일치가 아니라 **수치 일치와 결론 일치**로 판정해야 한다. 수치는 어차피 엔진에서 오므로 결정론적이다.

## §7 실패 처리

```
생성 → 검사 실패
   │
   ├─ 1차 재생성   위반 항목을 프롬프트에 명시해 피드백
   │                 "직전 응답에서 {{unknown_key}}를 사용했습니다.
   │                  허용 목록에 있는 자리표시자만 쓰십시오."
   │
   ├─ 2차 재생성   동일 방식 1회 추가
   │
   └─ 최종 실패    GUARDRAIL_BLOCKED 반환 + 알림
```

| 상황 | 처리 |
| --- | --- |
| 섹션 하나만 실패 | 해당 섹션만 `null`. 나머지 섹션은 정상 반환 |
| 엔진 값 대조 실패 | 재생성 없이 즉시 차단 + 알림 ([§5.2](#gate-out)) |
| RAG 결과 0건 | 생성 진행하되 "관련 자료를 찾지 못했습니다" 고정 문구 |
| 엔진 데이터 부족 | 생성 시도하지 않음. `INSUFFICIENT_DATA` |
| 2회 재생성 후 실패 | `GUARDRAIL_BLOCKED` + 실패 프롬프트·응답 전문 보관 |

재생성 시 **위반 내용을 구체적으로 알려줘야** 고쳐진다. "형식을 지키세요"로는 같은 실수를 반복한다. 어떤 key가 문제였는지, 어떤 문장이 걸렸는지를 그대로 넣는다.

## §7.1 버전 관리

**프롬프트는 코드가 아니라 데이터로 다룬다.** 소스에 하드코딩하면 수정할 때마다 배포가 필요하고, 어떤 버전이 어떤 응답을 만들었는지 추적할 수 없다.

| 항목 | 규칙 |
| --- | --- |
| 저장 | 파일 또는 DB. 기능별 · 계층별로 분리 |
| 버전 태그 | `briefing.v3` 형식. 의미 변경 시에만 증가 |
| 응답 로그 | `prompt_version`, `model`, `effort`, `cache_read_tokens` 기록 |
| 롤백 | 이전 버전 태그로 즉시 전환 가능해야 함 |
| A/B | 사용자 해시 기반 분기. 평가셋으로 전후 비교 후 승격 |

> **피드백과의 연결**
> API의 `POST /feedback`에서 수집하는 `reasons`가 이 문서의 우선순위를 결정한다. `wrong_number`가 많으면 [§3](#numbers)과 출력단 검사를, `too_generic`이 많으면 [§2](#shape)의 구조와 Wiki 활용을 손본다. **프롬프트를 감으로 고치지 않기 위한 장치**이므로 피드백 UI는 Phase 1부터 붙인다.
